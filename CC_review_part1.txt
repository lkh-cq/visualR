## Hard-constraint answers

**packet_id ↔ Merge seam (§4.1):** The Phase-6 resolution is **correct and effectively airtight** for the round's packet set. `materialize_adjacency` pairs reference envelope `packet_id`s; `.packet_merge_map` is built from the same `packets` argument, and a pair referencing an absent id fails closed. Residual caveats: `.packet_merge_map` itself lacks a duplicate-id check (relies on `materialize_adjacency`'s upstream duplicate rejection), and the "consumed once" invariant (§1.7) is not enforced — a custom policy emitting overlapping edges would double-consume a Merge until the duplicate packet_id surfaces next round.

**merge_id determinism (14.4):** **Holds** in the reviewed code. `harmony_step`'s merge_id is a pure function of (left_id, right_id, operator, logical_time, addr_key); `.visualR_harmony_state$counter` is dead code and not in the id path. Pairing order is deterministic (radix-sorted packet_ids); the two RNG policies self-reset via `set.seed(round)` so identical inputs → identical permutations across serial/PSOCK. Latent hazards if touched later: the dead counter, and the global-RNG mutation inside policies.
